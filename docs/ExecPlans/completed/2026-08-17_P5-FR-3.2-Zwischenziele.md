## Purpose / Big Picture

FR-3.2 aus `docs/01_Funktionale_Anforderungen.md` lautet: „Zu jedem Monat können Zwischenziele
definiert werden (z. B. ‚Kapitel 3 abschließen')." Die Anforderung hat die Priorität **Must** und
ist damit Kern des MS4-Prototyps. Sie ist **nicht umgesetzt**. Die vorhandene Dokumentation erklärt
das Notizfeld eines Planungseintrags zum Ersatz (`docs/MS4_Fachliche_Dokumentation.md`, Zeile 168,
und `docs/MS4_Testabschlussbericht.md`, Zeile 272). Das ist keine Umsetzung, sondern eine Umgehung:
Ein Zwischenziel ohne die Möglichkeit, es abzuhaken und seinen Erfüllungsgrad zu sehen, ist kein
Zwischenziel, sondern eine Notiz an einem Termin.

Nach diesem Plan kann eine Studentin auf der Seite „Planung" für einen Monat eine Liste von
Zwischenzielen führen: anlegen („Kapitel 3 abschließen"), optional mit einem Tag im Monat
versehen, abhaken, wenn sie fertig ist, und löschen. Über der Liste steht ein Zähler in der Form
„1 / 4". Auf dem Dashboard erscheint derselbe Zähler für den laufenden Monat, damit der
Erfüllungsgrad ohne Umweg sichtbar ist.

Sichtbar wird das so: Nach `flask db upgrade`, `flask run --debug` und `ng serve` zeigt
http://localhost:4200/planning unter den geplanten Lernzeiten einen Abschnitt „Zwischenziele
<Monat>". Ein Eintrag lässt sich anlegen, das Kästchen davor lässt sich anklicken, der Zähler
springt von „0 / 1" auf „1 / 1", und nach `F5` steht alles noch so da.

Nach Abschluss dieses Plans ist **jede Must-Anforderung** aus
`docs/01_Funktionale_Anforderungen.md` mindestens in Grundzügen umgesetzt, mit einer Ausnahme:
FR-2.1 (Grobplanung mit Wochenbudget aus dem ECTS-Workload) bleibt teilweise offen, weil das
Wochenbudget fehlt. Das ist bewusst nicht Teil dieses Plans.

## Surprises & Discoveries

- Beobachtung: `docs/05_Datenmodell.md` beschreibt in Abschnitt 3.6 bereits eine Tabelle
  `milestones` — allerdings gegen eine Tabelle `modules`, die nie gebaut wurde. In der tatsächlichen
  Umsetzung trägt die Tabelle `goals` das Modul als Freitext in der Spalte `module_name`.
  Evidenz: `backend/app/models/` enthält vier Modelle (`Goal`, `PlanSlot`, `StudySession`, `User`),
  kein `Module`. Das Zielbild im Datenmodell und der gebaute Code sind an dieser Stelle
  auseinandergelaufen. Folge: Der Entwurf wird angepasst übernommen, siehe `Decision Log`.

- Beobachtung: Die Tests laufen gegen SQLite im Arbeitsspeicher und erzeugen das Schema mit
  `db.create_all()` statt über die Migrationen.
  Evidenz: `backend/app/config.py` setzt in `TestingConfig`
  `SQLALCHEMY_DATABASE_URI = "sqlite:///:memory:"`; `backend/tests/conftest.py` ruft
  `_db.create_all()`. **Folge: Ein grüner `pytest`-Lauf beweist nicht, dass die neue Migration
  funktioniert.** Die Migration muss zusätzlich von Hand gegen PostgreSQL geprüft werden (M1).

## Decision Log

- Entscheidung: Ein Zwischenziel hängt an einem Lernziel (`goal_id`), nicht an einem Modul, und
  das Feld ist optional.
  Begründung: Die in `docs/05_Datenmodell.md` vorgesehene Verknüpfung `module_id` verweist auf eine
  Tabelle `modules`, die es im Code nicht gibt. Das Lernziel ist die nächstliegende vorhandene
  Entsprechung — es trägt das Modul als Text und ist bereits mit `plan_slots` und `study_sessions`
  auf dieselbe Weise verknüpft. Optional bleibt die Verknüpfung, weil der Gestaltungsentwurf
  `docs/design-reference/html/2a-dashboard.html` auch modulunabhängige Einträge zeigt
  („Gliederung Projektbericht").
  Datum/Autor: 2026-08-17, Team.

- Entscheidung: Der Monat wird als zwei ganze Zahlen `year` und `month` gespeichert, nicht als
  Datum des Monatsersten.
  Begründung: Die Tabelle `plan_slots` handhabt es bereits genau so
  (`backend/app/models/plan_slot.py`), und die Planungsseite im Frontend filtert über einen
  Schlüssel der Form `2026-08`, den sie in zwei Zahlen zerlegt. Ein abweichender Typ für dieselbe
  Sache würde denselben Filter zweimal verschieden bauen lassen. Die im Datenmodell vorgesehene
  Prüfregel, dass ein optionaler Feintermin im selben Monat liegen muss, bleibt inhaltlich
  erhalten: Statt eines vollen Datums speichert die Tabelle nur den Tag im Monat (`due_day`), der
  gegen die Länge genau dieses Monats geprüft wird und deshalb gar nicht aus ihm herausfallen kann.
  Datum/Autor: 2026-08-17, Team.

- Entscheidung: Ein Zwischenziel bekommt keine Priorität, keine Note und keine Fortschrittsrechnung.
  Begründung: `docs/05_Datenmodell.md` grenzt Zwischenziele ausdrücklich gegen Lernziele ab —
  Zwischenziele sind kurzfristige Arbeitspakete eines Monats, Lernziele spannen den
  Sechs-Monats-Horizont. FR-3.2 verlangt nur „definieren"; das Abhaken kommt aus dem
  Gestaltungsentwurf hinzu, weil ein Zwischenziel ohne Erledigt-Zustand nutzlos wäre.
  Datum/Autor: 2026-08-17, Team.

## Context and Orientation

### Was diese Anwendung ist

Der Lernzeit-Manager ist eine Web-Anwendung für Studierende: Lernziele über ein halbes Jahr planen,
Lernzeit per Stoppuhr erfassen, Fortschritt auswerten. Sie besteht aus zwei Teilen in einem
gemeinsamen Repository:

- `backend/` — ein Server in Python mit dem Web-Rahmenwerk **Flask**, der eine Schnittstelle unter
  `/api/...` bereitstellt und über die Bibliothek **SQLAlchemy** mit einer PostgreSQL-Datenbank
  spricht. Schema-Änderungen laufen über **Alembic** (eingebunden als Flask-Migrate): Jede Änderung
  ist eine nummerierte Python-Datei unter `backend/migrations/versions/`, angewendet mit
  `flask db upgrade`.
- `frontend/` — eine Einzelseiten-Anwendung in TypeScript mit **Angular** (Version 22). Der Browser
  lädt die Seite einmal, danach tauscht Angular nur noch Ausschnitte aus.

Die Datenbank läuft lokal in einem Docker-Container, beschrieben in `docker-compose.yml` im
Repository-Wurzelverzeichnis.

### Der Stand, auf dem dieser Plan aufsetzt

Es gibt vier Tabellen, angelegt durch `backend/migrations/versions/0001_ms4_initial_schema.py`:

- `users` — Benutzerkonten. Die Anmeldung läuft über ein Zugriffstoken (ein signiertes Merkmal, das
  der Browser bei jeder Anfrage mitschickt), umgesetzt mit der Bibliothek Flask-JWT-Extended. Jede
  Adresse außer `/api/health`, `/api/auth/register` und `/api/auth/login` ist geschützt.
- `goals` — Lernziele mit Titel, Zieldatum, Modulname als Freitext, ECTS-Punkten und Status.
- `plan_slots` — geplante Lernzeiten. Ein Eintrag hat `year` und `month` als ganze Zahlen und
  optional einen `day`. Fehlt der Tag, ist es eine Monatsplanung.
- `study_sessions` — die per Stoppuhr erfasste Lernzeit.

Die Oberfläche hat vier geschützte Seiten, verdrahtet in `frontend/src/app/app.routes.ts`:
Dashboard (`/`), Lernziele (`/goals`), Planung (`/planning`) und Timer (`/timer`).

Die für diesen Plan wichtigste Datei ist `frontend/src/app/features/planning/planning.ts`. Sie
enthält Vorlage und Logik in einer Datei — die übliche Bauform der Feature-Seiten dieses Projekts —
und führt bereits einen Monatsfilter: Das Feld `selectedMonth` hält einen Schlüssel der Form
`2026-08`, `availableMonths()` erzeugt die Auswahl von einem Monat rückwärts bis sieben Monate
voraus, und `loadSlots()` zerlegt den Schlüssel in `year` und `month`. Der neue Abschnitt hängt
sich an genau diesen Filter.

### Die Regeln dieses Projekts, die hier gelten

Jede Prüfung eingehender Daten steht in `backend/app/validation.py`. Jede Funktion dort prüft genau
eine Sache, liefert bei Erfolg den bereinigten Wert und wirft sonst `ValidationError`. Diese
Ausnahme wird in `backend/app/__init__.py` zentral in eine Antwort mit Status 400 und dem Rumpf
`{"error": "..."}` übersetzt. Neue Prüfungen gehören dorthin und nirgendwo anders hin.

Jede Abfrage filtert auf den angemeldeten Benutzer, jeder Einzelzugriff endet auf `first_or_404()`.
Ein fremder Datensatz liefert damit HTTP 404 und nicht 403 — die Existenz fremder Daten wird nicht
verraten. Das Muster steht in `backend/app/routes/plans.py` und ist hier genau zu übernehmen.

Alle Zeitpunkte werden in koordinierter Weltzeit (UTC) gespeichert und mit angehängtem `Z`
ausgeliefert. Zuständig ist `iso_utc` aus `backend/app/time_utils.py`. Wer eine Zeitspalte
ausliefert, benutzt diese Funktion und nicht `datetime.isoformat()`.

Angular hängt jedem Formular mit `ngModel` automatisch `novalidate` an. Deshalb wirken die
HTML-Attribute `min`, `max` und `required` in diesen Formularen **nicht**, und jede Prüfung muss
ausdrücklich in TypeScript stehen.

## Concrete Steps

### M1 — Migration 0003 legt die Tabelle `milestones` an

**Schritt 1.1.** Zuerst feststellen, auf welche Vorgängerversion die neue Migration zeigen muss.
In `backend/` bei aktiver virtueller Umgebung:

    flask db heads

Erwartete Ausgabe, wenn der Plan P4 bereits umgesetzt ist:

    0002_goal_prioritaet_und_ergebnis (head)

Ist P4 noch nicht umgesetzt, lautet die Ausgabe:

    0001_ms4_initial_schema (head)

Der ausgegebene Bezeichner ist genau der Wert, der unten bei `down_revision` einzutragen ist.
Stimmt er nicht, bricht Alembic später mit `Can't locate revision identified by ...` ab. Zeigt
`flask db heads` **zwei** Zeilen an, sind zwei Migrationen parallel entstanden — dann nicht
weiterarbeiten, sondern im Team klären, welche zuerst gilt.

**Schritt 1.2.** Neue Datei `backend/migrations/versions/0003_milestones.py`. Im folgenden Inhalt
ist `down_revision` gegebenenfalls auf den in Schritt 1.1 ermittelten Wert anzupassen:

    """Zwischenziele je Monat (FR-3.2)

    Revision ID: 0003_milestones
    Revises: 0002_goal_prioritaet_und_ergebnis
    Create Date: 2026-08-17

    Ein Zwischenziel ist ein kurzfristiges Arbeitspaket innerhalb eines Monats,
    zum Beispiel "Kapitel 3 abschliessen". Es haengt optional an einem Lernziel.
    Monat und Jahr sind ganze Zahlen - genau wie in plan_slots, damit beide
    Tabellen mit demselben Filter abgefragt werden koennen.
    """

    import sqlalchemy as sa
    from alembic import op

    revision = "0003_milestones"
    down_revision = "0002_goal_prioritaet_und_ergebnis"
    branch_labels = None
    depends_on = None


    def upgrade():
        op.create_table(
            "milestones",
            sa.Column("id", sa.Integer(), nullable=False),
            sa.Column("user_id", sa.Integer(), nullable=False),
            sa.Column("goal_id", sa.Integer(), nullable=True),
            sa.Column("title", sa.String(length=200), nullable=False),
            sa.Column("year", sa.Integer(), nullable=False),
            sa.Column("month", sa.Integer(), nullable=False),
            sa.Column("due_day", sa.Integer(), nullable=True),
            sa.Column("done", sa.Boolean(), nullable=False, server_default=sa.false()),
            sa.Column("created_at", sa.DateTime(), nullable=True),
            sa.ForeignKeyConstraint(["goal_id"], ["goals.id"]),
            sa.ForeignKeyConstraint(["user_id"], ["users.id"]),
            sa.PrimaryKeyConstraint("id"),
        )


    def downgrade():
        op.drop_table("milestones")

Das `server_default=sa.false()` ist wichtig: Ohne es hätte eine bestehende Zeile beim späteren
Hinzufügen weiterer Spalten keinen definierten Wert für `done`. Die Tabelle ist zwar neu und leer,
aber der Standardwert gehört trotzdem in die Datenbank und nicht nur in den Python-Code, damit auch
ein direkter `INSERT` über pgAdmin eine gültige Zeile erzeugt.

**Schritt 1.3.** Anwenden:

    flask db upgrade

Erwartete Ausgabe, sinngemäß:

    INFO  [alembic.runtime.migration] Running upgrade 0002_goal_prioritaet_und_ergebnis -> 0003_milestones

Bricht der Befehl mit `could not connect to server` ab, läuft der Docker-Container nicht:
`docker compose up -d` im Repository-Wurzelverzeichnis nachholen.

**Schritt 1.4.** Nachweisen, dass die Tabelle wirklich in PostgreSQL steht — das kann `pytest` in
diesem Projekt nicht leisten, weil die Tests gegen SQLite laufen. In pgAdmin 4 die Datenbank
`lernzeit` öffnen, Rechtsklick, *Query Tool*:

    SELECT column_name, data_type, is_nullable
    FROM information_schema.columns
    WHERE table_name = 'milestones'
    ORDER BY ordinal_position;

Erwartet: neun Zeilen — `id`, `user_id`, `goal_id`, `title`, `year`, `month`, `due_day`, `done`,
`created_at`.

**Schritt 1.5.** Die Rückwärtsrichtung einmal ausprobieren:

    flask db downgrade
    flask db upgrade

Beides ohne Fehlermeldung; danach steht die Datenbank wieder auf `0003_milestones`.

**Akzeptanz M1:** `flask db upgrade` läuft durch, die SQL-Abfrage zeigt neun Spalten,
`flask db downgrade` gefolgt von `flask db upgrade` läuft fehlerfrei.

### M2 — Modell `Milestone` und Einbindung in die Anwendung

**Schritt 2.1.** Neue Datei `backend/app/models/milestone.py`:

    from datetime import datetime, timezone

    from ..extensions import db
    from ..time_utils import iso_utc


    class Milestone(db.Model):
        """Ein monatliches Zwischenziel (FR-3.2).

        Abgegrenzt zum Lernziel (Goal): Ein Zwischenziel ist ein kurzfristiges
        Arbeitspaket innerhalb eines Monats - "Kapitel 3 abschliessen" - ohne
        Note, ohne Prioritaet und ohne Fortschrittsrechnung. Das Lernziel
        spannt dagegen den Sechs-Monats-Horizont.
        """

        __tablename__ = "milestones"

        id = db.Column(db.Integer, primary_key=True)
        user_id = db.Column(db.Integer, db.ForeignKey("users.id"), nullable=False)
        goal_id = db.Column(db.Integer, db.ForeignKey("goals.id"), nullable=True)
        title = db.Column(db.String(200), nullable=False)
        year = db.Column(db.Integer, nullable=False)
        month = db.Column(db.Integer, nullable=False)
        due_day = db.Column(db.Integer, nullable=True)
        done = db.Column(db.Boolean, nullable=False, default=False)
        created_at = db.Column(db.DateTime, default=lambda: datetime.now(timezone.utc))

        user = db.relationship("User", back_populates="milestones")
        goal = db.relationship("Goal", back_populates="milestones")

        def to_dict(self) -> dict:
            return {
                "id": self.id,
                "user_id": self.user_id,
                "goal_id": self.goal_id,
                "title": self.title,
                "year": self.year,
                "month": self.month,
                "due_day": self.due_day,
                "done": self.done,
                "created_at": iso_utc(self.created_at),
            }

**Schritt 2.2.** Die Gegenstücke der Beziehungen anlegen. SQLAlchemy verlangt bei
`back_populates`, dass beide Seiten sich kennen; fehlt eine Seite, bricht die Anwendung beim Start
mit `Mapper 'Mapper[User(users)]' has no property 'milestones'` ab.

In `backend/app/models/user.py` neben die vorhandenen Beziehungen (`goals`, `plan_slots`,
`study_sessions`) anfügen:

    milestones = db.relationship("Milestone", back_populates="user", cascade="all, delete-orphan")

In `backend/app/models/goal.py` neben `plan_slots` und `study_sessions` anfügen:

    milestones = db.relationship("Milestone", back_populates="goal")

Bewusster Unterschied: Beim Lernziel steht **kein** `cascade="all, delete-orphan"`. Wird ein
Lernziel gelöscht, sollen seine Zwischenziele nicht mitverschwinden, sondern verwaisen — die
Spalte `goal_id` ist ohnehin optional. Das Gegenteil wäre unangenehm: Ein Zwischenziel wie
„Gliederung Projektbericht" überlebt es, wenn das zugehörige Lernziel neu zugeschnitten wird.
Damit das funktioniert, muss `delete_goal` in `backend/app/routes/goals.py` die Verknüpfung vorher
lösen; siehe Schritt 3.5.

**Schritt 2.3.** In `backend/app/models/__init__.py` anmelden. Aus:

    from .goal import Goal
    from .plan_slot import PlanSlot
    from .study_session import StudySession
    from .user import User

    __all__ = ["User", "Goal", "PlanSlot", "StudySession"]

wird:

    from .goal import Goal
    from .milestone import Milestone
    from .plan_slot import PlanSlot
    from .study_session import StudySession
    from .user import User

    __all__ = ["User", "Goal", "Milestone", "PlanSlot", "StudySession"]

**Schritt 2.4.** In `backend/app/__init__.py` in `create_app` die Importzeile der Modelle
erweitern. Aus:

    from .models import Goal, PlanSlot, StudySession, User  # noqa: F401

wird:

    from .models import Goal, Milestone, PlanSlot, StudySession, User  # noqa: F401

Der Kommentar `# noqa: F401` unterdrückt die Lint-Warnung „importiert, aber nicht benutzt" — der
Import ist trotzdem nötig, weil SQLAlchemy die Modelle nur kennt, wenn ihre Klassen einmal geladen
wurden.

**Schritt 2.5.** Prüfen, dass die Anwendung überhaupt noch startet:

    cd backend
    ruff check .
    pytest -q

Erwartet: `All checks passed!` und ein grüner Lauf. Schlägt jeder Test mit einem `Mapper`-Fehler
fehl, fehlt eine der beiden Beziehungen aus Schritt 2.2.

**Akzeptanz M2:** `pytest` ist grün, und `flask shell` gefolgt von `from app.models import Milestone`
läuft ohne Fehler.

## Idempotence and Recovery

Alle Schritte sind mehrfach ausführbar. `flask db upgrade` erkennt an der Tabelle `alembic_version`,
welche Migrationen bereits gelaufen sind, und tut beim zweiten Aufruf nichts. `docker compose up -d`
ist ebenfalls wiederholbar.

Geht bei der Migration in M1 etwas schief:

    flask db downgrade
    flask db upgrade

Hilft das nicht, ist die lokale Datenbank vollständig zurücksetzbar — sie enthält nur Testdaten:

    docker compose down -v
    docker compose up -d
    cd backend
    flask db upgrade

`docker compose down -v` löscht das Datenvolumen `pgdata` und damit alle lokalen Daten. Im
Entwicklungsbetrieb unbedenklich, auf Railway niemals anzuwenden.

Nach Abschluss bleibt die Umgebung sauber: keine temporären Dateien, keine geänderten
Konfigurationen. `backend/requirements.txt` und `frontend/package.json` werden von diesem Plan
**nicht** angefasst.

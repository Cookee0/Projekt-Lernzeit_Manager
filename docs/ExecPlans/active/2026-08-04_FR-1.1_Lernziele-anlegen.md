## Purpose / Big Picture

Heute kann die Anwendung nichts. Wer `http://localhost:4200` aufruft, sieht die Angular-Startseite mit dem Angular-Logo. Die Datenbank enthält keine einzige Tabelle. Das Backend kennt genau einen Endpoint, `GET /api/health`, der `{"status": "ok"}` zurückgibt.

Nach diesem Plan kann eine Studentin im Browser Folgendes tun: Sie öffnet `http://localhost:4200`, wird auf die Seite „Lernziele" geleitet, klickt auf „Neues Lernziel", tippt „Modul ISEF01 abschließen" ein, wählt als Zieldatum den 28.02.2027 (also gut sechs Monate in der Zukunft) und klickt auf „Speichern". Sie landet zurück auf der Übersicht und sieht ihr Lernziel dort in einer Liste stehen, sortiert nach Zieldatum. Sie drückt F5 – das Ziel ist immer noch da, denn es liegt jetzt in PostgreSQL. Legt sie ein zweites Ziel mit einem früheren Zieldatum an, rutscht dieses in der Liste nach oben.

Das ist der beobachtbare Gewinn: **aus einer leeren Beispiel-App wird eine Anwendung, die persistente Lernziele über einen beliebig langen Planungshorizont aufnimmt und geordnet anzeigt.**

Technisch entsteht dabei die erste Datenbanktabelle des Projekts, die erste Alembic-Migration, der erste fachliche API-Blueprint und die erste echte Angular-Seite. Alles Spätere baut darauf auf.

Installiert war v22.14.0 unter `G:\Programmieren\nodejs`.
  Beleg: `npx ng lint` lieferte „The Angular CLI requires a minimum Node.js version of v22.22.3 or v24.15.0 or v26.0.0.“, Exit-Code 3, keinerlei Lint-Ausgabe.
- Beobachtung: `G:\Programmieren\nodejs\node.exe` gehört unter Windows dem Konto `SYSTEM`/`Administratoren` (ACL zeigt nur `ReadAndExecute` für den aktuellen Benutzer); ein direktes Überschreiben scheitert mit „Permission denied“, auch außerhalb der Werkzeug-Sandbox.
  Beleg: `Get-Acl` zeigte `Owner: NT-AUTORITÄT\SYSTEM`, `IsReadOnly: False`, aber `cp` scheiterte trotzdem mit „Permission denied“.
- Lösung (nur für diese Sitzung, keine dauerhafte Änderung am System): Node v22.23.2 (aktuelle 22.x-LTS „Jod“) wurde von `https://nodejs.org/dist/v22.23.2/node-v22.23.2-win-x64.zip` nach `C:\Users\lelle\AppData\Local\node-v22.23.2-win-x64\` entpackt (ein Ordner, den der Benutzer selbst besitzt) und für die jeweilige Shell-Sitzung per `export PATH="/c/Users/lelle/AppData/Local/node-v22.23.2-win-x64:$PATH"` vorangestellt. Alle Frontend-Befehle in diesem Plan (`ng lint`, `ng test`, `ng serve`) wurden danach über `./node_modules/.bin/ng …` statt über den globalen `npx`-Wrapper aufgerufen, weil `npx.cmd` in `G:\Programmieren\nodejs` sonst weiterhin dessen eigenes, altes `node.exe` verwendet hätte statt des neu vorangestellten PATH-Eintrags.

Ist die Version zu alt, hilft entweder ein Update des global installierten Node (offizieller Installer von nodejs.org, LTS-Zweig) oder derselbe Workaround: eine neuere Node-Version an einen selbst beschreibbaren Ort entpacken und für die Sitzung vorn an `PATH` stellen.

## Context and Orientation

Dieser Abschnitt beschreibt das Repository so, als würdest du es zum ersten Mal sehen. Alle Pfade sind relativ zum Repository-Wurzelverzeichnis.

### Was das Projekt ist

Ein Studienprojekt der IU im Modul ISEF01. Gebaut wird der „Lernzeit-Manager", eine Web-Anwendung, mit der Studierende Lernziele planen, Lernzeit per Stoppuhr erfassen und ihren Fortschritt auswerten. Die vollständige Anforderungsliste steht in `docs/01_Funktionale_Anforderungen.md`.

### Der Technologie-Stack

Das Repository ist ein Monorepo mit zwei Anwendungen:

- **`backend/`** – eine Python-3.12-Anwendung mit dem Web-Framework **Flask**. Sie stellt eine REST-API bereit, also HTTP-Endpoints, die JSON zurückgeben. Datenbankzugriff läuft über **Flask-SQLAlchemy** (ein sogenanntes ORM: man beschreibt Tabellen als Python-Klassen statt SQL zu schreiben) und Schemaänderungen über **Flask-Migrate/Alembic** (Migrationen: versionierte Python-Dateien, die die Datenbankstruktur schrittweise verändern). Tests laufen mit **pytest**, Linting mit **ruff**.
- **`frontend/`** – eine **Angular-22**-Anwendung in TypeScript. Angular ist ein Framework für Single-Page-Applications: eine einzige HTML-Seite, in der JavaScript die Inhalte austauscht, statt bei jedem Klick eine neue Seite vom Server zu laden. Tests laufen mit **vitest**, Linting mit **ESLint** über `ng lint`.

Die Datenbank ist **PostgreSQL 16** und läuft lokal in einem Docker-Container, definiert in `docker-compose.yml` im Wurzelverzeichnis.

### Der Ist-Zustand des Backends

`backend/app/__init__.py` enthält eine sogenannte *Application Factory* – eine Funktion, die eine konfigurierte Flask-Anwendung erzeugt und zurückgibt. Aktuell sieht sie exakt so aus:

    from flask import Flask
    from flask_cors import CORS

    from .config import config_by_name
    from .extensions import db, migrate


    def create_app(config_name: str = "development") -> Flask:
        app = Flask(__name__)
        app.config.from_object(config_by_name[config_name])

        CORS(app, origins=app.config.get("CORS_ORIGINS", ["http://localhost:4200"]))

        db.init_app(app)
        migrate.init_app(app, db)

        from .routes.health import health_bp
        app.register_blueprint(health_bp)

        return app

Ein *Blueprint* ist in Flask ein Bündel zusammengehöriger Endpoints, das man am Ende an die Anwendung anmeldet. Der einzige existierende Blueprint liegt in `backend/app/routes/health.py`:

    from flask import Blueprint, jsonify

    health_bp = Blueprint("health", __name__)


    @health_bp.get("/api/health")
    def health():
        return jsonify({"status": "ok"}), 200

Beachte den Stil: Der Blueprint bekommt **kein** `url_prefix`, sondern der vollständige Pfad steht im Decorator. Diesen Stil übernehmen wir für die Lernziele, weil `docs/golden-principles.md` Punkt 3 vorgibt, vorhandenem Stil zu folgen.

`backend/app/extensions.py` erzeugt die geteilten Erweiterungsobjekte:

    from flask_migrate import Migrate
    from flask_sqlalchemy import SQLAlchemy

    db = SQLAlchemy()
    migrate = Migrate()

`backend/app/config.py` definiert vier Konfigurationen. Wichtig für dich: `TestingConfig` benutzt `sqlite:///:memory:`, also eine flüchtige SQLite-Datenbank im Arbeitsspeicher. Tests brauchen deshalb **kein** laufendes PostgreSQL. `DevelopmentConfig` liest `DATABASE_URL` aus der Umgebung und fällt sonst auf `postgresql://lernzeit:lernzeit_dev@localhost:5432/lernzeit` zurück.

`backend/tests/conftest.py` stellt zwei pytest-Fixtures bereit (Fixtures sind wiederverwendbare Bausteine, die pytest automatisch in Testfunktionen einsetzt, wenn deren Parametername passt):

    import pytest
    from flask.testing import FlaskClient

    from app import create_app


    @pytest.fixture
    def app():
        return create_app("testing")


    @pytest.fixture
    def client(app) -> FlaskClient:
        return app.test_client()

**Hier fehlt etwas Entscheidendes:** Es werden keine Tabellen angelegt. Solange es keine Modelle gab, war das egal. Sobald wir das erste Modell haben, würde jeder Datenbankzugriff im Test mit `no such table: goals` scheitern. Meilenstein 2 repariert das.

`backend/migrations/` existiert (durch `flask db init` erzeugt), enthält aber **kein Verzeichnis `versions/`** – es gibt also bisher null Migrationen. Die erste Migration entsteht in Meilenstein 1. `backend/pyproject.toml` schließt `migrations/` vom ruff-Linting aus; an automatisch generierten Migrationsdateien musst du also nicht formatieren.

### Zwei Angular-Eigenheiten, die du kennen musst

**Erstens: Diese Anwendung ist „zoneless".** In `frontend/package.json` fehlt die Abhängigkeit `zone.js`, und in `app.config.ts` steht kein `provideZoneChangeDetection()`. Angular 22 erkennt Änderungen also nicht mehr automatisch daran, dass irgendein Callback gelaufen ist. Praktische Folge: **Zustand, der die Anzeige beeinflusst, muss in einem `signal()` liegen.** Ein `signal` ist ein Container für einen Wert; `wert()` liest ihn, `wert.set(neu)` schreibt ihn und sagt Angular gleichzeitig, dass neu gerendert werden muss. Schreibst du stattdessen `this.goals = daten` auf ein normales Feld, ändert sich die Anzeige nicht, und du suchst den Fehler lange. Alle Komponenten in diesem Plan benutzen deshalb Signals.

**Zweitens: Die Dateinamens-Konvention ist neu.** Angular 22 erzeugt `goal-list.ts`, nicht `goal-list.component.ts`. Die Klasse heißt `GoalList`, nicht `GoalListComponent`. Das siehst du an der vorhandenen `app.ts` mit der Klasse `App`. Halte dich daran, sonst passt der Code nicht zum Rest.

### Wie API und Frontend zusammenspielen

Das Backend läuft auf Port 5000, das Frontend auf Port 4200. Das sind für den Browser zwei verschiedene Ursprünge („Origins"), und aus Sicherheitsgründen blockiert der Browser solche Anfragen standardmäßig. Deshalb ist in `backend/app/__init__.py` bereits `CORS(app, origins=["http://localhost:4200"])` konfiguriert – Flask schickt damit einen Antwort-Header, der dem Browser die Anfrage erlaubt. Du musst daran nichts ändern; wenn im Browser trotzdem ein CORS-Fehler erscheint, läuft mit hoher Wahrscheinlichkeit schlicht das Backend nicht.

**Ziel dieses Meilensteins:** In der PostgreSQL-Datenbank existiert danach eine Tabelle `goals` mit den Spalten `id`, `title`, `target_date` und `created_at`. Vorher gab es im gesamten Projekt keine einzige Tabelle. Am Ende kannst du die Tabelle in pgAdmin 4 sehen und mit SQL abfragen.

Ein *Modell* ist eine Python-Klasse, die eine Datenbanktabelle beschreibt. Eine *Migration* ist eine generierte Python-Datei, die den Unterschied zwischen dem alten und dem neuen Datenbankschema als ausführbare Anweisungen enthält (`op.create_table(...)`). Migrationen werden immer committet, damit alle im Team dieselbe Datenbankstruktur bekommen.

### Schritt 1.1 – Verzeichnis und Modell anlegen

Erstelle das Verzeichnis `backend/app/models/`.

Erstelle `backend/app/models/goal.py` mit exakt diesem Inhalt:

    from ..extensions import db


    class Goal(db.Model):
        """Ein Lernziel mit Titel und Zieldatum (FR-1.1)."""

        __tablename__ = "goals"

        id = db.Column(db.Integer, primary_key=True)
        title = db.Column(db.String(200), nullable=False)
        target_date = db.Column(db.Date, nullable=False)
        created_at = db.Column(
            db.DateTime(timezone=True),
            nullable=False,
            default=lambda: datetime.now(timezone.utc),
        )

        def to_dict(self) -> dict:
            """Wandelt das Lernziel in ein JSON-taugliches Dictionary um."""
            return {
                "id": self.id,
                "title": self.title,
                "target_date": self.target_date.isoformat(),
                "created_at": self.created_at.isoformat(),

Erläuterungen zu einzelnen Zeilen, damit nichts geraten werden muss:

- `__tablename__ = "goals"` legt den Tabellennamen fest. Ohne diese Zeile würde SQLAlchemy einen Namen aus dem Klassennamen ableiten; explizit ist eindeutiger.
- `db.Date` speichert ein reines Datum ohne Uhrzeit. Genau das ist ein Zieldatum.
- `created_at` dient nur der Nachvollziehbarkeit („wann wurde das Ziel angelegt") und taucht in keiner Eingabemaske auf. `default=lambda: datetime.now(timezone.utc)` sorgt dafür, dass der Zeitstempel beim Speichern automatisch gesetzt wird. Die `lambda` ist wichtig: Ohne sie würde der Zeitpunkt des Programmstarts eingefroren und bei jedem Ziel derselbe stehen.
- `to_dict` gibt `target_date` als ISO-Zeichenkette (`"2027-02-28"`) zurück, weil `jsonify` mit einem Python-`date`-Objekt sonst ein schwer lesbares RFC-Format erzeugt.

### Schritt 2.2 – Den Blueprint für Lernziele anlegen

Erstelle `backend/app/routes/goals.py` mit exakt diesem Inhalt:

    from datetime import date

    from flask import Blueprint, jsonify, request

    from ..extensions import db
    from ..models import Goal

    goals_bp = Blueprint("goals", __name__)

    MAX_TITLE_LENGTH = 200


    def validate_goal_payload(payload: object) -> tuple[dict, dict]:
        """Prüft die Eingabedaten für ein Lernziel.

        Gibt ein Tupel (werte, fehler) zurück. Ist `fehler` leer, sind `werte`
        gültig und können direkt an das Modell übergeben werden. Ist `fehler`
        nicht leer, ordnet es jedem fehlerhaften Feldnamen eine deutsche
        Fehlermeldung zu.
        """
        if not isinstance(payload, dict):
            return {}, {"body": "Es wird ein JSON-Objekt erwartet."}

        values: dict = {}
        errors: dict = {}

        title = payload.get("title")
        if not isinstance(title, str) or not title.strip():
            errors["title"] = "Titel ist erforderlich."
        elif len(title.strip()) > MAX_TITLE_LENGTH:
            errors["title"] = f"Titel darf höchstens {MAX_TITLE_LENGTH} Zeichen lang sein."
        else:
            values["title"] = title.strip()

        target_date = payload.get("target_date")
        if not isinstance(target_date, str) or not target_date:
            errors["target_date"] = "Zieldatum ist erforderlich."
        else:
            try:
                values["target_date"] = date.fromisoformat(target_date)
            except ValueError:
                errors["target_date"] = "Zieldatum muss im Format JJJJ-MM-TT vorliegen."

        return values, errors


    @goals_bp.get("/api/goals")
    def list_goals():
        """Gibt alle Lernziele zurück, sortiert nach Zieldatum aufsteigend."""
        goals = (
            db.session.execute(db.select(Goal).order_by(Goal.target_date, Goal.id))
            .scalars()
            .all()
        )
        return jsonify([goal.to_dict() for goal in goals]), 200


    @goals_bp.post("/api/goals")
    def create_goal():
        """Legt ein neues Lernziel an."""
        values, errors = validate_goal_payload(request.get_json(silent=True))
        if errors:
            return jsonify({"errors": errors}), 400

        goal = Goal(title=values["title"], target_date=values["target_date"])
        db.session.add(goal)
        db.session.commit()
        return jsonify(goal.to_dict()), 201

Erläuterungen:

- `request.get_json(silent=True)` gibt `None` zurück, statt eine Ausnahme zu werfen, wenn der Anfragekörper kein gültiges JSON ist. Das `isinstance`-Prüfung am Anfang der Validierung fängt diesen Fall ab und liefert eine saubere 400 statt eines Server-Fehlers.
- `date.fromisoformat("2027-02-28")` erzeugt ein `date`-Objekt. Bei `"31.02.2027"` oder `"31.01.2027 "` wirft es `ValueError`, was wir in eine Feldfehlermeldung übersetzen.
- `title.strip()` entfernt führende und abschließende Leerzeichen. Ein Titel aus reinen Leerzeichen gilt damit als fehlend.
- Die Sortierung `order_by(Goal.target_date, Goal.id)` ist aufsteigend (Standard). Das zweite Kriterium `id` sorgt dafür, dass zwei Ziele mit gleichem Zieldatum immer in derselben, stabilen Reihenfolge erscheinen, statt bei jedem Aufruf zu springen.
- Es gibt bewusst **keine** Validierungsbibliothek. Für zwei Felder wäre das laut `docs/golden-principles.md` Punkt 2 überdimensioniert.

Achte darauf, dass keine Zeile länger als 100 Zeichen ist – das ist in `backend/pyproject.toml` als `line-length` festgelegt und wird von ruff geprüft.

    import { HttpClient } from '@angular/common/http';
    import { Injectable, inject } from '@angular/core';
    import { Observable } from 'rxjs';

    import { Goal, NewGoal } from './goal.model';

    /**
     * Kapselt alle HTTP-Aufrufe rund um Lernziele.
     *
     * Die Backend-URL steht bewusst nur hier. Wird das Frontend später auf
     * Railway deployt, muss genau diese eine Konstante ersetzt werden.
     */
    @Injectable({ providedIn: 'root' })
    export class GoalService {
      private readonly http = inject(HttpClient);
      private readonly baseUrl = 'http://localhost:5000/api/goals';

      /** Holt alle Lernziele, vom Backend nach Zieldatum sortiert. */
      list(): Observable<Goal[]> {
        return this.http.get<Goal[]>(this.baseUrl);
      }

      /** Legt ein Lernziel an und liefert das gespeicherte Ziel inklusive id zurück. */
      create(goal: NewGoal): Observable<Goal> {
        return this.http.post<Goal>(this.baseUrl, goal);
      }
    }

Ein `Observable` ist ein Objekt, das einen Wert liefert, sobald er da ist. Man erhält den Wert, indem man `subscribe(...)` aufruft. Wichtig: **Ohne `subscribe` wird die HTTP-Anfrage gar nicht abgeschickt.** `@Injectable({ providedIn: 'root' })` bedeutet, dass Angular genau eine Instanz dieses Service für die gesamte Anwendung erzeugt und sie überall dort einsetzt, wo `inject(GoalService)` steht.

          title: 'Projektbericht',
          target_date: '2027-02-28',
        });

          title: 'Projektbericht',
          target_date: '2027-02-28',

        });
      });
    });

`provideHttpClientTesting()` ersetzt die echte HTTP-Schicht durch eine Attrappe: Es geht keine Anfrage ins Netz. `expectOne(url)` behauptet, dass genau eine Anfrage an diese URL offen ist, und gibt sie zurück; `flush(daten)` beantwortet sie mit den angegebenen Daten. `httpMock.verify()` in `afterEach` schlägt fehl, wenn eine Anfrage offen blieb, die kein Test beantwortet hat – das deckt vergessene Aufrufe auf.

`describe`, `it`, `expect` und `beforeEach` sind global verfügbar, weil `frontend/tsconfig.spec.json` `"types": ["vitest/globals"]` setzt. Du musst nichts aus `vitest` importieren.

    import { Component, inject, signal } from '@angular/core';
    import { FormBuilder, ReactiveFormsModule, Validators } from '@angular/forms';
    import { Router, RouterLink } from '@angular/router';

    import { GoalService } from '../goal.service';

    @Component({
      selector: 'app-goal-form',
      imports: [ReactiveFormsModule, RouterLink],
      templateUrl: './goal-form.html',
      styleUrl: './goal-form.scss',
    })
    export class GoalForm {
      private readonly formBuilder = inject(FormBuilder);
      private readonly goalService = inject(GoalService);
      private readonly router = inject(Router);

      protected readonly saving = signal(false);
      protected readonly serverError = signal<string | null>(null);

      protected readonly form = this.formBuilder.nonNullable.group({
        title: ['', [Validators.required, Validators.maxLength(200)]],
        target_date: ['', Validators.required],
      });

      protected submit(): void {
        if (this.form.invalid) {
          this.form.markAllAsTouched();
          return;
        }

        this.saving.set(true);
        this.serverError.set(null);

        this.goalService.create(this.form.getRawValue()).subscribe({
          next: () => {
            void this.router.navigate(['/ziele']);
          },
          error: () => {
            this.serverError.set('Speichern fehlgeschlagen. Läuft das Backend?');
            this.saving.set(false);
          },
        });
      }
    }

Das `void` vor `this.router.navigate(...)` sagt ausdrücklich, dass das zurückgegebene Promise absichtlich nicht weiterverwendet wird.

## Idempotence and Recovery

Fast alle Schritte sind gefahrlos wiederholbar. `docker compose up -d`, `npm install`, `pip install -r requirements-dev.txt`, `flask db upgrade`, `ruff check .`, `pytest`, `ng lint` und `ng test` kannst du beliebig oft ausführen.

Die eine Ausnahme ist `flask db migrate`: Jeder Aufruf erzeugt eine **neue** Datei in `backend/migrations/versions/`. Führst du ihn versehentlich zweimal aus, entsteht beim zweiten Mal entweder eine leere Migration („No changes in schema detected", dann wird keine Datei angelegt) oder eine doppelte. Lösche in dem Fall die überflüssige Datei, **bevor** du `flask db upgrade` ausführst.

Ist die lokale Datenbank in einem unklaren Zustand, setzt du sie im Wurzelverzeichnis vollständig zurück:

    docker compose down -v
    docker compose up -d
    cd backend
    flask db upgrade

`docker compose down -v` löscht das Datenvolumen und damit **alle lokalen Daten**. Das ist hier unproblematisch, weil es nur Testdaten sind – laut `docs/02_Qualitaetsanforderungen.md` dürfen ohnehin keine echten personenbezogenen Daten in der Entwicklungsumgebung liegen.

Willst du den gesamten Plan verwerfen, verlässt du den Feature-Branch:

    git checkout main
    git branch -D feature/fr-1.1-lernziele-anlegen

Die lokale Datenbank behält dann die Tabelle `goals`. Das stört nicht; ein späterer `flask db upgrade` erkennt den Zustand korrekt. Willst du auch das zurücksetzen, benutze `docker compose down -v` wie oben.

Am Ende sollten keine Hilfsdateien übrig bleiben. `.env`, `.venv/`, `node_modules/` und `__pycache__/` sind in `.gitignore` aufgeführt und gehören nicht in einen Commit. Prüfe vor dem Push mit `git status`, dass nichts davon zum Commit vorgemerkt ist.

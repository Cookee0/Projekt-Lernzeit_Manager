## Purpose / Big Picture

Nach FR-1.1 kann man ein Lernziel mit Titel und Zieldatum anlegen. Was fehlt, merkt man beim ersten realistischen Gebrauch: Auf der Liste stehen dann „Klausur", „Klausur" und „Klausur", und niemand weiß, zu welchem Modul das jeweils gehört oder ob das Ziel noch offen, gerade in Arbeit oder längst erreicht ist. Die Liste ist als Planungsübersicht damit wertlos.

Nach diesem Plan gilt: Beim Anlegen eines Lernziels muss zusätzlich das Modul beziehungsweise der Kurs angegeben werden („Projekt Software Engineering (ISEF01)"), und es lässt sich ein Status auswählen – *Offen*, *In Arbeit* oder *Erreicht*, voreingestellt ist *Offen*. Die Übersicht auf `/ziele` zeigt vier Spalten: Titel, Modul, Zieldatum, Status. Eine Studentin sieht damit auf einen Blick, welches Ziel zu welchem Modul gehört und wo sie steht.

Der beobachtbare Gewinn: **aus einer Liste austauschbarer Titel wird eine Übersicht, aus der Zugehörigkeit und Fortschritt ablesbar sind.**

## Decision Log

- Decision: Das Modul wird als **Freitext-Zeichenkette** direkt am Lernziel gespeichert (Spalte `module`, maximal 100 Zeichen). Es gibt **keine** eigene Modul-Tabelle.
  Rationale: FR-1.2 verlangt lediglich „zugeordnetes Modul/Kurs". Eine eigene Entität mit ECTS-Punkten wird erst von FR-2.1 gebraucht („Der Workload wird anhand der ECTS-Punkte des jeweiligen Moduls festgelegt"). Sie jetzt zu bauen, hieße ein zweites vollständiges CRUD (Anlegen/Bearbeiten/Löschen von Modulen) mit in diesen Plan zu nehmen, das FR-1.2 nicht fordert – ausgeschlossen durch `docs/golden-principles.md` Punkt 2. Der Plan zu FR-2.1 führt die Modul-Entität ein und überführt die vorhandenen Freitexte per Migration.
  Date/Author: 2026-08-04 / Claude Code (KI), Zuschnitt bestätigt durch Julian.

- Decision: Der Status wird als Zeichenkette mit den drei erlaubten Werten `offen`, `in_arbeit` und `erreicht` gespeichert, **nicht** als PostgreSQL-`ENUM`-Typ.
  Rationale: Ein Datenbank-Enum lässt sich später nur mit zusätzlichem, handgeschriebenem SQL erweitern; eine Zeichenkette mit Prüfung in der Anwendungsschicht ist migrationsfreundlich und für ein Team von drei Studierenden deutlich einfacher zu warten. Die Prüfung findet an einer Stelle statt (`validate_goal_payload` in `backend/app/routes/goals.py`).
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Gespeichert werden deutsche technische Werte (`offen`, `in_arbeit`, `erreicht`); die Anzeige-Beschriftungen (`Offen`, `In Arbeit`, `Erreicht`) stehen an genau einer Stelle im Frontend.
  Rationale: Die Oberfläche ist durchgehend deutsch, eine Übersetzungsschicht Englisch→Deutsch wäre reiner Zusatzaufwand. Der Unterstrich in `in_arbeit` vermeidet Leerzeichen in einem technischen Wert, was Filter- und URL-Parameter später einfacher macht.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Der Status kann in diesem Plan **beim Anlegen** gesetzt, aber noch **nicht nachträglich geändert** werden.
  Rationale: FR-1.2 verlangt nur, dass ein Lernziel einen Status *hat*. Das nachträgliche Ändern entsteht zwangsläufig mit dem Bearbeiten-Formular aus FR-1.3, und das gezielte „als erreicht markieren" ist eine eigene Anforderung (FR-5.1).   Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Die Migration wird nach dem Erzeugen **von Hand nachbearbeitet**, um Vorgabewerte für bereits vorhandene Datensätze zu setzen.

## Context and Orientation

Alle Pfade sind relativ zum Repository-Wurzelverzeichnis. Dieser Abschnitt beschreibt den Stand **nach** FR-1.1 vollständig, damit du ohne Vorwissen weiterarbeiten kannst.

### Das Projekt in zwei Sätzen

Ein Studienprojekt der IU (Modul ISEF01). Gebaut wird der „Lernzeit-Manager", eine Web-Anwendung zum Planen von Lernzielen und Erfassen von Lernzeit. Das Repository ist ein Monorepo: `backend/` enthält eine Flask-Anwendung (Python 3.12) mit REST-API, `frontend/` eine Angular-22-Anwendung (TypeScript), und `docker-compose.yml` im Wurzelverzeichnis startet PostgreSQL 16 in einem Container.

### Begriffe, die dieser Plan verwendet

- **Modell** – eine Python-Klasse, die eine Datenbanktabelle beschreibt (hier über die Bibliothek Flask-SQLAlchemy).
- **Migration** – eine versionierte Python-Datei unter `backend/migrations/versions/`, die die Datenbankstruktur schrittweise verändert. Erzeugt wird sie mit `flask db migrate`, angewendet mit `flask db upgrade`. Migrationen werden immer committet, damit alle im Team dieselbe Struktur bekommen.
- **Blueprint** – in Flask ein Bündel zusammengehöriger HTTP-Endpoints.
- **Signal** – in Angular ein Container für einen Wert (`wert()` liest, `wert.set(x)` schreibt). Diese Anwendung läuft „zoneless": In `frontend/package.json` fehlt `zone.js`. Angular erkennt Änderungen deshalb **ausschließlich** über Signals. Wer Anzeigezustand in ein normales Feld schreibt, sieht die Änderung nie im Browser.

### Schritt 1.3 – Migration von Hand um Vorgabewerte ergänzen

**Diesen Schritt nicht überspringen.** Öffne die eben erzeugte Datei unter `backend/migrations/versions/`. Ihre `upgrade`-Funktion sieht ungefähr so aus:

    def upgrade():
        op.add_column('goals', sa.Column('module', sa.String(length=100), nullable=False))
        op.add_column('goals', sa.Column('status', sa.String(length=20), nullable=False))

Ausgeführt auf einer Tabelle, die schon Zeilen enthält, scheitert das mit:

    psycopg2.errors.NotNullViolation: column "module" of relation "goals" contains null values

Der Grund: Die Spalte darf nicht leer sein, aber PostgreSQL hätte für die bestehenden Zeilen keinen Wert. Die Lösung ist Standardpraxis – man gibt beim Hinzufügen einen Vorgabewert mit, den die bestehenden Zeilen bekommen, und entfernt diesen Vorgabewert danach wieder, damit neue Datensätze weiterhin einen echten Wert liefern müssen.

Ersetze die `upgrade`-Funktion durch:

    def upgrade():
        # server_default versorgt bereits vorhandene Zeilen mit einem Wert.
        op.add_column(
            'goals',
            sa.Column(
                'module',
                sa.String(length=100),
                nullable=False,
                server_default='Nicht zugeordnet',
            ),
        )
        op.add_column(
            'goals',
            sa.Column(
                'status',
                sa.String(length=20),
                nullable=False,
                server_default='offen',
            ),
        )
        # Vorgabewert wieder entfernen: Neue Datensaetze muessen echte Werte liefern.
        op.alter_column('goals', 'module', server_default=None)
        op.alter_column('goals', 'status', server_default=None)

Prüfe außerdem, dass die `downgrade`-Funktion die Spalten wieder entfernt:

    def downgrade():
        op.drop_column('goals', 'status')
        op.drop_column('goals', 'module')

In Plan FR-1.1 stand, generierte Migrationen nicht von Hand zu bearbeiten. **Hier ist die Ausnahme**, und zwar eine notwendige: Neu erzeugen hilft nicht, weil Alembic den Vorgabewert nicht erraten kann. Migrationen von Hand nachzubearbeiten ist der dokumentierte Weg von Alembic für genau diesen Fall. Alles andere in der Datei (`revision`, `down_revision`, die Importe) bleibt unangetastet.

## Idempotence and Recovery

Wiederholbar ohne Risiko: `docker compose up -d`, `pip install -r requirements-dev.txt`, `npm install`, `flask db upgrade`, `ruff check .`, `pytest`, `npx ng lint`, `npx ng test`.

Nicht beliebig wiederholbar ist `flask db migrate`: Jeder Aufruf erzeugt eine neue Datei unter `backend/migrations/versions/`. Läuft er versehentlich zweimal, lösche die überzählige Datei, **bevor** du `flask db upgrade` ausführst. Eine bereits angewendete Migration darfst du nicht mehr einfach löschen – nimm sie stattdessen mit `flask db downgrade` zurück:

    flask db downgrade

Das führt die `downgrade`-Funktion der zuletzt angewendeten Migration aus und entfernt hier die Spalten `module` und `status` samt ihrem Inhalt. Danach kannst du die Datei löschen und neu erzeugen.

Gerät die lokale Datenbank in einen unklaren Zustand, setze sie komplett zurück (im Wurzelverzeichnis):

    docker compose down -v
    docker compose up -d
    cd backend
    flask db upgrade

`docker compose down -v` löscht das Datenvolumen und damit alle lokalen Lernziele. Das ist unproblematisch, weil es Testdaten sind; laut `docs/02_Qualitaetsanforderungen.md` dürfen in der Entwicklungsumgebung ohnehin keine echten personenbezogenen Daten liegen. Ein Nebeneffekt ist sogar nützlich: Nach dem Zurücksetzen ist keine Zeile mehr mit `Nicht zugeordnet` befüllt.

Den gesamten Plan verwerfen:

    git checkout main
    git branch -D feature/fr-1.2-lernziel-pflichtfelder

Achtung: Die lokale Datenbank behält dann die Spalten `module` und `status`, während der Code auf `main` sie nicht mehr kennt. Das stört Flask nicht (überzählige Spalten werden ignoriert), aber `flask db migrate` würde sie beim nächsten Mal als „zu entfernen" erkennen. Setze die Datenbank in diesem Fall wie oben mit `docker compose down -v` zurück.

Vor jedem Push mit `git status` prüfen, dass weder `.env`, `.venv/`, `node_modules/` noch `__pycache__/` zum Commit vorgemerkt sind. Alle stehen in `.gitignore`.

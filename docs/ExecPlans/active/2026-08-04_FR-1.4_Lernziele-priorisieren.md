## Purpose / Big Picture

Nach FR-1.1 bis FR-1.3 lassen sich Lernziele anlegen, mit Modul und Status versehen, bearbeiten, verschieben und löschen. Was noch fehlt, merkt man, sobald zwölf Ziele in der Liste stehen: Sie wirken alle gleich wichtig. Ob die Klausur in vier Wochen wichtiger ist als das Nachlesen eines Kapitels, steht nirgends – die Sortierung nach Zieldatum sagt nur etwas über *wann*, nichts über *wie wichtig*.

Nach diesem Plan gilt: Beim Anlegen und Bearbeiten lässt sich optional eine Priorität wählen – *Hoch*, *Mittel* oder *Niedrig*, voreingestellt ist „– keine –". Die Übersicht auf `/ziele` zeigt eine zusätzliche Spalte „Priorität", in der eine gesetzte Priorität als farbig hinterlegte Markierung erscheint (Hoch rot, Mittel gelb, Niedrig grau) und eine fehlende schlicht als Gedankenstrich.

Der beobachtbare Gewinn: **eine Studentin sieht in der Übersicht auf einen Blick, welche ihrer Ziele wichtig sind, statt alle gleich zu gewichten.**

## Decision Log

- Decision: Die Priorität ist **optional**. Die Datenbankspalte `priority` erlaubt `NULL`, und in der Oberfläche steht die Auswahl anfangs auf „– keine –".
  Rationale: FR-1.4 sagt „Lernziele **können** priorisiert werden" – ein Angebot, keine Pflicht. Eine erzwungene Priorität würde außerdem alle bereits vorhandenen Lernziele zu einem erfundenen Wert zwingen. Als angenehmer Nebeneffekt braucht die Migration dadurch **keine** manuelle Nachbearbeitung: Eine Spalte, die `NULL` sein darf, lässt sich einer gefüllten Tabelle ohne Weiteres hinzufügen. In FR-1.2 war das bei `module` und `status` anders und musste von Hand geregelt werden.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Die Priorität wird als Zeichenkette mit den erlaubten Werten `hoch`, `mittel` und `niedrig` gespeichert, **nicht** als Zahl (etwa 1/2/3) und nicht als PostgreSQL-`ENUM`-Typ.
  Rationale: FR-1.4 nennt genau diese drei Stufen als Beispiel. Zahlen wären ohne Legende nicht lesbar (ist 1 die höchste oder die niedrigste Stufe?), und ein Datenbank-Enum ließe sich später nur mit handgeschriebenem SQL erweitern. Die Lösung ist bewusst dieselbe wie beim Status aus FR-1.2 – zwei gleichartige Felder sollen nicht unterschiedlich funktionieren.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Die Liste wird **nicht** nach Priorität sortiert und **nicht** danach gefiltert. Sie bleibt nach Zieldatum sortiert; die Priorität erscheint nur als farbige Markierung.
  Rationale: FR-1.4 verlangt, Ziele priorisieren zu **können**, nicht, die Liste danach zu ordnen. Eine Sortierumschaltung oder ein Filter wären Zusatzfunktionen, nach denen niemand gefragt hat – ausgeschlossen durch `docs/golden-principles.md` Punkt 2. Die farbige Markierung erfüllt den fachlichen Zweck („auf einen Blick sehen, was wichtig ist"), ohne die bewährte Sortierung nach Zieldatum aufzugeben, an der die gesamte Planungssicht hängt.   Date/Author: 2026-08-04 / Claude Code (KI).

### Das Projekt in zwei Sätzen

Ein Studienprojekt der IU (Modul ISEF01). Gebaut wird der „Lernzeit-Manager", eine Web-Anwendung zum Planen von Lernzielen und Erfassen von Lernzeit. Das Repository ist ein Monorepo: `backend/` enthält eine Flask-Anwendung (Python 3.12) mit REST-API, `frontend/` eine Angular-22-Anwendung (TypeScript), und `docker-compose.yml` im Wurzelverzeichnis startet PostgreSQL 16 in einem Container.

### Begriffe, die dieser Plan verwendet

- **Modell** – eine Python-Klasse, die eine Datenbanktabelle beschreibt (Bibliothek Flask-SQLAlchemy).
- **Migration** – eine versionierte Datei unter `backend/migrations/versions/`, die die Datenbankstruktur schrittweise verändert. Erzeugt mit `flask db migrate`, angewendet mit `flask db upgrade`. Migrationen werden immer committet.
- **`NULL`** – der Datenbankwert für „kein Wert vorhanden". Nicht dasselbe wie eine leere Zeichenkette: `NULL` heißt „nicht gesetzt", `""` heißt „gesetzt, aber leer". Genau diesen Unterschied brauchen wir hier.
- **Signal** – in Angular ein Container für einen Wert (`wert()` liest, `wert.set(x)` schreibt). Diese Anwendung läuft „zoneless": In `frontend/package.json` fehlt `zone.js`. Angular erkennt Änderungen **ausschließlich** über Signals. Anzeigezustand in einem normalen Feld ändert im Browser sichtbar nichts.

## Meilenstein 1 – Die Spalte `priority`

**Ziel:** Danach hat die Tabelle `goals` in PostgreSQL eine zusätzliche Spalte `priority`, die leer bleiben darf. Bereits vorhandene Lernziele behalten dort `NULL`.

### Schritt 1.1 – Modell erweitern

Öffne `backend/app/models/goal.py`. Ergänze die Spalte und den Eintrag in `to_dict()`, sodass die Klasse danach so aussieht:

    class Goal(db.Model):
        """Ein Lernziel mit Titel, Modul, Zieldatum, Status und Prioritaet."""

        __tablename__ = "goals"

        id = db.Column(db.Integer, primary_key=True)
        title = db.Column(db.String(200), nullable=False)
        module = db.Column(db.String(100), nullable=False)
        target_date = db.Column(db.Date, nullable=False)
        status = db.Column(db.String(20), nullable=False, default="offen")
        priority = db.Column(db.String(20), nullable=True)
        created_at = db.Column(
            db.DateTime(timezone=True),
            nullable=False,
            default=lambda: datetime.now(timezone.utc),
        )

        def to_dict(self) -> dict:
            """Wandelt das Lernziel in ein JSON-taugliches Dictionary um."""
            return {
                "id": self.id,
                "title": self.title,
                "module": self.module,
                "target_date": self.target_date.isoformat(),
                "status": self.status,
                "priority": self.priority,
                "created_at": self.created_at.isoformat(),

`nullable=True` ist hier die entscheidende Angabe – sie erlaubt „keine Priorität". Beachte, dass `priority` in `to_dict()` **ohne** Umwandlung durchgereicht wird: Ist der Wert `None`, macht `jsonify` daraus im JSON automatisch `null`.

Die Übersicht unter `/ziele` zeigt eine Spalte „Priorität". Eine gesetzte Priorität erscheint als „Hoch", „Mittel" oder „Niedrig" mit farbiger Hinterlegung, eine fehlende als grauer Gedankenstrich. Die technischen Werte `hoch`, `mittel`, `niedrig` erscheinen nirgends auf der Oberfläche.

Eine Priorität lässt sich setzen, ändern und wieder entfernen, und der Zustand bleibt nach einem Neuladen der Seite erhalten.

In PostgreSQL enthält die Tabelle `goals` die Spalte `priority` (`character varying(20)`, `nullable`). Vor diesem Plan existierte sie nicht. Bereits vorhandene Lernziele tragen dort `NULL`.

## Idempotence and Recovery

Wiederholbar ohne Risiko: `docker compose up -d`, `pip install -r requirements-dev.txt`, `npm install`, `flask db upgrade`, `ruff check .`, `pytest`, `npx ng lint`, `npx ng test`.

Nicht beliebig wiederholbar ist `flask db migrate`: Jeder Aufruf erzeugt eine neue Datei unter `backend/migrations/versions/`. Läuft er versehentlich zweimal, lösche die überzählige Datei, **bevor** du `flask db upgrade` ausführst. Eine bereits angewendete Migration darfst du nicht einfach löschen – nimm sie stattdessen zurück:

    flask db downgrade

Das führt die `downgrade`-Funktion der zuletzt angewendeten Migration aus und entfernt hier die Spalte `priority` samt ihrem Inhalt. Danach kannst du die Datei löschen und neu erzeugen.

Gerät die lokale Datenbank in einen unklaren Zustand, setze sie im Wurzelverzeichnis vollständig zurück:

    docker compose down -v
    docker compose up -d
    cd backend
    flask db upgrade

`docker compose down -v` löscht das Datenvolumen und damit alle lokalen Lernziele. Das ist unproblematisch, weil es Testdaten sind; laut `docs/02_Qualitaetsanforderungen.md` dürfen in der Entwicklungsumgebung ohnehin keine echten personenbezogenen Daten liegen.

Den gesamten Plan verwerfen:

    git checkout main
    git branch -D feature/fr-1.4-lernziele-priorisieren

Achtung: Die lokale Datenbank behält dann die Spalte `priority`, während der Code auf `main` sie nicht mehr kennt. Flask stört das nicht (überzählige Spalten werden ignoriert), aber ein späteres `flask db migrate` würde sie als „zu entfernen" erkennen. Setze die Datenbank in diesem Fall wie oben mit `docker compose down -v` zurück.

Vor jedem Push mit `git status` prüfen, dass weder `.env`, `.venv/`, `node_modules/` noch `__pycache__/` zum Commit vorgemerkt sind. Alle stehen in `.gitignore`.

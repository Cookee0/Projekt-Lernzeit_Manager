## Purpose / Big Picture

Nach FR-1.1 und FR-1.2 kann man Lernziele anlegen und ansehen – aber nie wieder ändern. Das ist in der Praxis unhaltbar: Klausurtermine werden verschoben, ein Modul wird umbenannt, ein Tippfehler im Titel bleibt für immer stehen, ein versehentlich angelegtes Ziel verstopft dauerhaft die Übersicht. Und weil der Status bisher nur beim Anlegen gesetzt werden kann, bleibt ein Ziel für immer „Offen", auch wenn die Klausur längst bestanden ist.

Nach diesem Plan gilt: In der Übersicht unter `/ziele` hat jede Zeile die beiden Aktionen „Bearbeiten" und „Löschen". „Bearbeiten" öffnet dasselbe Formular wie beim Anlegen, nur bereits gefüllt mit den bisherigen Werten; Titel, Modul, Zieldatum und Status lassen sich ändern und speichern. „Löschen" fragt direkt in der Zeile nach („Wirklich löschen?") und entfernt das Ziel erst nach Bestätigung – ein Fehlklick löscht also nichts.

Der beobachtbare Gewinn: **aus einer Liste, in die man nur hineinschreiben kann, wird eine Planung, die man pflegen kann.** Ein Klausurtermin, der sich um drei Wochen verschiebt, ist danach eine Sache von zehn Sekunden, und ein erreichtes Ziel lässt sich endlich auch als „Erreicht" markieren.

## Decision Log

- Decision: „Verschieben" bekommt **keine** eigene Funktion und keinen eigenen Endpoint. Ein Zieldatum wird über das normale Bearbeiten-Formular geändert.
  Rationale: FR-1.3 nennt „bearbeitet, verschoben oder gelöscht" in einem Atemzug. Ein Verschieben ist fachlich exakt eine Änderung des Feldes `target_date`. Ein zusätzlicher Endpoint `POST /api/goals/<id>/verschieben` würde dieselbe Wirkung mit mehr Code erzielen und wäre eine spekulative Abstraktion im Sinne von `docs/golden-principles.md` Punkt 2. Der Nachweis für „verschoben" wird in der Abnahme dennoch ausdrücklich geführt: Ein Test ändert nur das Zieldatum, und im manuellen Durchstich wird ein Ziel um Wochen verschoben und wandert dadurch in der sortierten Liste an eine andere Stelle.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Zum Ändern wird `PUT` verwendet, nicht `PATCH`. Ein `PUT` erwartet **alle** Felder, genau wie das Anlegen.
  Rationale: Die Oberfläche schickt ohnehin immer das komplette Formular. `PATCH` mit teilweisen Änderungen bräuchte eine zweite, andersartige Validierungslogik („Feld fehlt" wäre dort kein Fehler, sondern die Anweisung, es unverändert zu lassen). Mit `PUT` lässt sich die bereits existierende Funktion `validate_goal_payload` unverändert wiederverwenden – ein Endpoint mehr, aber keine zweite Validierungsregel.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Das Bearbeiten-Formular ist **dieselbe Komponente** wie das Anlegen-Formular (`GoalForm`), gesteuert über die Route.
  Rationale: Beide Masken zeigen dieselben vier Felder mit denselben Prüfungen. Zwei Komponenten hieße, jede künftige Feldänderung an zwei Stellen nachzuziehen – FR-1.4 fügt gleich als Nächstes ein weiteres Feld hinzu. Der Unterschied zwischen den Modi beträgt wenige Zeilen: eine Überschrift, ein Ladevorgang beim Öffnen und die Wahl zwischen `create` und `update` beim Speichern.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Die Löschbestätigung erfolgt **in der Tabellenzeile**, nicht über den Browser-Dialog `confirm()`.
  Rationale: Ein `confirm()` lässt sich in Tests nur durch Manipulation eines globalen Browser-Objekts prüfen, was den Test von einer Umgebungseigenschaft abhängig macht statt vom eigenen Code. Die Rückfrage in der Zeile ist mit einem Signal und zwei Schaltflächen gebaut, vollständig testbar, blockiert die Seite nicht und lässt sich mit „Abbrechen" folgenlos verlassen. Ganz ohne Rückfrage zu löschen wäre keine Option: Ein Fehlklick würde unwiederbringlich Daten vernichten.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Gelöscht wird endgültig (`DELETE FROM goals`), nicht über eine Markierung „gelöscht" (sogenanntes Soft Delete).
  Rationale: FR-1.3 verlangt Löschen, nicht Archivieren. Ein Soft Delete zwänge jede spätere Abfrage dazu, gelöschte Zeilen auszufiltern, und niemand hat danach gefragt. FR-5.3 („Historie aller erreichten Ziele") betrifft *erreichte*, nicht gelöschte Ziele und ist mit Priorität „Could" ohnehin ein eigenes Thema.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Ein `DELETE` auf ein nicht existierendes Lernziel antwortet mit HTTP 404, nicht mit 204.
  Rationale: Beide Varianten sind vertretbar. 404 wurde gewählt, weil sie ehrlicher ist und sich testen lässt: Zweimaliges Löschen desselben Ziels liefert erst 204, dann 404, und genau das prüft ein Test. Für die Oberfläche macht es keinen Unterschied, weil sie die gelöschte Zeile sofort entfernt.
  Date/Author: 2026-08-04 / Claude Code (KI).

- Decision: Bearbeitet wird auf einer **eigenen Seite** unter `/ziele/:id/bearbeiten`, nicht in einem Seitenpanel neben der Liste.
  Rationale: Der Entwurf `docs/design-reference/2b-lernziele.png` zeigt das Bearbeiten in einem rechts neben der Liste eingeblendeten Panel mit den Schaltflächen „Speichern", „Verschieben" und „Löschen". Das Team hat sich am 04.08.2026 bewusst dagegen entschieden: Ein Panel bräuchte zusätzlichen Zustand (offen/geschlossen, welches Ziel), müsste Anlegen und Bearbeiten in derselben Ansicht unterbringen und ist deutlich aufwendiger zu testen. Eine eigene Route erfüllt dieselbe Anforderung mit der bereits vorhandenen Formularkomponente. **Wichtig für später:** Der Wechsel auf ein Panel wäre eine reine Darstellungsänderung – API, Datenmodell und `GoalService` bleiben davon unberührt. Die im Entwurf eigenständige Schaltfläche „Verschieben" entfällt hier, weil das Zieldatum im Formular ohnehin änderbar ist (siehe die Entscheidung dazu weiter oben).
  Date/Author: 2026-08-04 / Julian (Teamentscheidung), festgehalten von Claude Code (KI).

## Context and Orientation

Alle Pfade sind relativ zum Repository-Wurzelverzeichnis. Dieser Abschnitt beschreibt den Stand **nach** FR-1.1 und FR-1.2 vollständig.

### Das Projekt in zwei Sätzen

Ein Studienprojekt der IU (Modul ISEF01). Gebaut wird der „Lernzeit-Manager", eine Web-Anwendung zum Planen von Lernzielen und Erfassen von Lernzeit. Das Repository ist ein Monorepo: `backend/` enthält eine Flask-Anwendung (Python 3.12) mit REST-API, `frontend/` eine Angular-22-Anwendung (TypeScript), und `docker-compose.yml` im Wurzelverzeichnis startet PostgreSQL 16 in einem Container.

### Begriffe, die dieser Plan verwendet

- **REST-Endpoint** – eine URL zusammen mit einer HTTP-Methode (`GET` = lesen, `POST` = neu anlegen, `PUT` = vollständig ersetzen, `DELETE` = löschen).
- **Blueprint** – in Flask ein Bündel zusammengehöriger Endpoints. Alle Lernziel-Endpoints liegen im Blueprint `goals_bp` in `backend/app/routes/goals.py`.
- **Route (Angular)** – die Zuordnung eines Adresspfads im Browser zu einer Komponente, definiert in `frontend/src/app/app.routes.ts`.
- **Signal** – in Angular ein Container für einen Wert (`wert()` liest, `wert.set(x)` schreibt, `wert.update(fn)` ändert ihn abhängig vom bisherigen Wert). Diese Anwendung läuft „zoneless": In `frontend/package.json` fehlt `zone.js`. Angular erkennt Änderungen deshalb **ausschließlich** über Signals. Anzeigezustand in einem normalen Feld führt dazu, dass sich im Browser sichtbar nichts tut.
- **Migration** – eine versionierte Datei unter `backend/migrations/versions/`, die die Datenbankstruktur verändert. **Dieser Plan braucht keine**: Es kommt kein Feld hinzu, es werden nur bestehende Daten geändert und gelöscht.

## Meilenstein 1 – API: einzelnes Lernziel lesen, ändern, löschen

**Ziel:** Danach kann ein HTTP-Client ein einzelnes Lernziel über seine Kennung abrufen, es vollständig überschreiben und es löschen. Nicht existierende Kennungen führen zu einer sauberen 404 statt zu einem Serverfehler. Zehn neue Tests belegen das.

### Schritt 1.1 – Die drei Endpoints ergänzen

Öffne `backend/app/routes/goals.py`. Füge **am Ende der Datei**, unterhalb der bestehenden Funktion `create_goal()`, die folgenden drei Funktionen an:

    @goals_bp.get("/api/goals/<int:goal_id>")
    def get_goal(goal_id: int):
        """Gibt ein einzelnes Lernziel zurueck."""
        goal = db.session.get(Goal, goal_id)
        if goal is None:
            return jsonify({"errors": {"id": "Lernziel nicht gefunden."}}), 404

        return jsonify(goal.to_dict()), 200


    @goals_bp.put("/api/goals/<int:goal_id>")
    def update_goal(goal_id: int):
        """Ersetzt alle Felder eines Lernziels. Aendert auch das Zieldatum (FR-1.3)."""
        goal = db.session.get(Goal, goal_id)
        if goal is None:
            return jsonify({"errors": {"id": "Lernziel nicht gefunden."}}), 404

        values, errors = validate_goal_payload(request.get_json(silent=True))
        if errors:
            return jsonify({"errors": errors}), 400

        goal.title = values["title"]
        goal.module = values["module"]
        goal.target_date = values["target_date"]
        goal.status = values["status"]
        db.session.commit()

        return jsonify(goal.to_dict()), 200


    @goals_bp.delete("/api/goals/<int:goal_id>")
    def delete_goal(goal_id: int):
        """Loescht ein Lernziel endgueltig."""
        goal = db.session.get(Goal, goal_id)
        if goal is None:
            return jsonify({"errors": {"id": "Lernziel nicht gefunden."}}), 404

        db.session.delete(goal)
        db.session.commit()

        return "", 204

Erläuterungen zu den Stellen, an denen man sich sonst verrennt:

- `<int:goal_id>` im Pfad bedeutet: Flask nimmt diesen Teil der URL, prüft, dass es eine ganze Zahl ist, wandelt sie um und übergibt sie als Parameter `goal_id`. Ein Aufruf von `/api/goals/abc` führt dadurch automatisch zu einer 404, ohne dass du etwas dafür tun musst. Ohne das `int:` bekämst du eine Zeichenkette und müsstest selbst umwandeln.
- `db.session.get(Goal, goal_id)` sucht anhand des Primärschlüssels und gibt `None` zurück, wenn nichts gefunden wird. Das ist der Grund für die `if goal is None`-Prüfung – ohne sie liefe der nächste Zugriff in einen `AttributeError` und damit in eine HTTP 500.
- Die Reihenfolge in `update_goal` ist bewusst: erst nachsehen, ob das Ziel überhaupt existiert (404), dann die Eingabe prüfen (400). Ein `PUT` auf eine nicht existierende Kennung mit gleichzeitig fehlerhaften Daten meldet damit den grundlegenderen Fehler.
- `return "", 204` gibt einen leeren Rumpf zurück. Bei HTTP 204 („No Content") ist genau das vorgeschrieben; `jsonify` wäre hier falsch.
- Es sind **keine** neuen Importe nötig. `db`, `Goal`, `jsonify`, `request` und `validate_goal_payload` sind alle bereits in dieser Datei vorhanden.

### Schritt 3.1 – Komponente um den Bearbeiten-Modus erweitern

Ersetze den gesamten Inhalt von `frontend/src/app/goals/goal-form/goal-form.ts` durch:

    import { Component, inject, signal } from '@angular/core';
    import { FormBuilder, ReactiveFormsModule, Validators } from '@angular/forms';
    import { ActivatedRoute, Router, RouterLink } from '@angular/router';

    import { GOAL_STATUS_LABELS, GoalStatus } from '../goal.model';
    import { GoalService } from '../goal.service';

    @Component({
      selector: 'app-goal-form',
      imports: [ReactiveFormsModule, RouterLink],
      templateUrl: './goal-form.html',
      styleUrl: './goal-form.scss',
    })
    export class GoalForm {
      private readonly formBuilder = inject(FormBuilder);
      private readonly goalService = inject(GoalService);
      private readonly router = inject(Router);
      private readonly route = inject(ActivatedRoute);

      /** Kennung des zu bearbeitenden Ziels, oder null beim Anlegen. */
      protected readonly goalId = this.leseGoalIdAusRoute();
      protected readonly isEdit = this.goalId !== null;

      protected readonly statusLabels = GOAL_STATUS_LABELS;
      protected readonly saving = signal(false);
      protected readonly loading = signal(false);
      protected readonly serverError = signal<string | null>(null);

      protected readonly form = this.formBuilder.nonNullable.group({
        title: ['', [Validators.required, Validators.maxLength(200)]],
        module: ['', [Validators.required, Validators.maxLength(100)]],
        target_date: ['', Validators.required],
        status: this.formBuilder.nonNullable.control<GoalStatus>('offen', Validators.required),
      });

      constructor() {
        if (this.goalId === null) {
          return;
        }

        this.loading.set(true);
        this.goalService.get(this.goalId).subscribe({
          next: (goal) => {
            this.form.setValue({
              title: goal.title,
              module: goal.module,
              target_date: goal.target_date,
              status: goal.status,
            });
            this.loading.set(false);
          },
          error: () => {
            this.serverError.set('Das Lernziel konnte nicht geladen werden.');
            this.loading.set(false);
          },
        });
      }

      protected submit(): void {
        if (this.form.invalid) {
          this.form.markAllAsTouched();
          return;
        }

        this.saving.set(true);
        this.serverError.set(null);

        const werte = this.form.getRawValue();
        const anfrage =
          this.goalId === null
            ? this.goalService.create(werte)
            : this.goalService.update(this.goalId, werte);

        anfrage.subscribe({
          next: () => {
            void this.router.navigate(['/ziele']);
          },
          error: () => {
            this.serverError.set('Speichern fehlgeschlagen. Läuft das Backend?');
            this.saving.set(false);
          },
        });
      }

      /** Liest die Kennung aus der Adresse. Gibt null zurueck, wenn keine vorhanden ist. */
      private leseGoalIdAusRoute(): number | null {
        const rohwert = this.route.snapshot.paramMap.get('id');
        if (rohwert === null) {
          return null;
        }

        const id = Number(rohwert);
        return Number.isInteger(id) && id > 0 ? id : null;
      }
    }

Erläuterungen zu den Stellen, an denen man sich sonst verrennt:

- **Reihenfolge der Felder.** `route` muss **vor** `goalId` stehen. TypeScript wertet Feldinitialisierungen von oben nach unten aus; stünde `goalId` zuerst, wäre `this.route` beim Aufruf noch `undefined` und du bekämst einen Laufzeitfehler.
- `this.route.snapshot.paramMap.get('id')` liest den Teil der Adresse, der in der Routendefinition `:id` heißt. `snapshot` bedeutet: der Wert im Moment des Öffnens. Das reicht hier, weil man vom Bearbeiten eines Ziels nie direkt zum Bearbeiten eines anderen wechselt, ohne die Seite zu verlassen.
- Die Prüfung `Number.isInteger(id) && id > 0` fängt Adressen wie `/ziele/abc/bearbeiten` ab. Die Komponente verhält sich dann wie beim Anlegen, statt eine sinnlose Anfrage an `/api/goals/NaN` zu schicken.
- `form.setValue({...})` verlangt, dass **alle** Felder angegeben werden – genau das wollen wir hier, denn ein vergessenes Feld wäre ein Fehler. Die verwandte Methode `patchValue` wäre nachsichtiger und würde ein Vergessen stillschweigend durchgehen lassen.
- Der Konstruktor bricht mit `return` ab, wenn keine Kennung vorliegt. Im Anlegen-Modus wird also keine HTTP-Anfrage geschickt – wichtig, weil die vorhandenen Tests aus FR-1.2 mit `httpMock.verify()` prüfen, dass keine unerwarteten Anfragen offen bleiben.

### Schritt 4.1 – Listenkomponente erweitern

Öffne `frontend/src/app/goals/goal-list/goal-list.ts`. Ergänze innerhalb der Klasse `GoalList` zwei weitere Signals und drei Methoden. Die Datei sieht danach so aus:

    import { Component, inject, signal } from '@angular/core';
    import { DatePipe } from '@angular/common';
    import { RouterLink } from '@angular/router';

    import { GOAL_STATUS_LABELS, Goal } from '../goal.model';
    import { GoalService } from '../goal.service';

    @Component({
      selector: 'app-goal-list',
      imports: [RouterLink, DatePipe],
      templateUrl: './goal-list.html',
      styleUrl: './goal-list.scss',
    })
    export class GoalList {
      private readonly goalService = inject(GoalService);

      protected readonly statusLabels = GOAL_STATUS_LABELS;
      protected readonly goals = signal<Goal[]>([]);
      protected readonly loading = signal(true);
      protected readonly error = signal<string | null>(null);

      /** Kennung des Ziels, fuer das gerade nachgefragt wird, oder null. */
      protected readonly pendingDeleteId = signal<number | null>(null);
      protected readonly deleteError = signal<string | null>(null);

      constructor() {
        this.goalService.list().subscribe({
          next: (goals) => {
            this.goals.set(goals);
            this.loading.set(false);
          },
          error: () => {
            this.error.set('Lernziele konnten nicht geladen werden. Läuft das Backend?');
            this.loading.set(false);
          },
        });
      }

      /** Blendet die Rueckfrage fuer eine Zeile ein. Loescht noch nichts. */
      protected askDelete(id: number): void {
        this.deleteError.set(null);
        this.pendingDeleteId.set(id);
      }

      /** Verwirft die Rueckfrage, ohne zu loeschen. */
      protected cancelDelete(): void {
        this.pendingDeleteId.set(null);
      }

      /** Loescht endgueltig und entfernt die Zeile aus der Anzeige. */
      protected confirmDelete(id: number): void {
        this.goalService.remove(id).subscribe({
          next: () => {
            this.goals.update((goals) => goals.filter((goal) => goal.id !== id));
            this.pendingDeleteId.set(null);
          },
          error: () => {
            this.deleteError.set('Löschen fehlgeschlagen. Läuft das Backend?');
            this.pendingDeleteId.set(null);
          },
        });
      }
    }

`this.goals.update((goals) => goals.filter(...))` erzeugt ein **neues** Array ohne das gelöschte Ziel und setzt es als neuen Wert des Signals. Wichtig ist das „neu": Würdest du das vorhandene Array mit `splice` verändern, bliebe es für Angular dasselbe Objekt und die Tabelle würde sich nicht aktualisieren. Die Alternative wäre, nach dem Löschen die komplette Liste erneut vom Server zu holen – das wäre eine überflüssige zweite Anfrage für ein Ergebnis, das wir bereits kennen.

### Schritt 4.2 – Template um eine Aktionsspalte erweitern

Öffne `frontend/src/app/goals/goal-list/goal-list.html`.

wird:

## Idempotence and Recovery

Alle Befehle dieses Plans sind gefahrlos wiederholbar: `docker compose up -d`, `pip install -r requirements-dev.txt`, `npm install`, `flask db upgrade`, `ruff check .`, `pytest`, `npx ng lint`, `npx ng test`. **Dieser Plan erzeugt keine Migration**, `flask db migrate` wird nicht aufgerufen, und damit entfällt die einzige nicht wiederholbare Operation der vorangegangenen Pläne.

Die eine wirklich unumkehrbare Aktion ist das Löschen eines Lernziels über die Oberfläche oder über `DELETE /api/goals/<id>`. Der Datensatz ist danach weg; es gibt weder Papierkorb noch Rückgängig-Funktion (siehe `Decision Log`). Beim manuellen Testen betrifft das ausschließlich selbst angelegte Testdaten. Laut `docs/02_Qualitaetsanforderungen.md` dürfen in der Entwicklungsumgebung ohnehin keine echten personenbezogenen Daten liegen.

Ist die lokale Datenbank in einem unklaren Zustand oder willst du mit sauberen Daten neu beginnen, setze sie im Wurzelverzeichnis vollständig zurück:

    docker compose down -v
    docker compose up -d
    cd backend
    flask db upgrade

Das löscht das Datenvolumen und legt das Schema aus den vorhandenen Migrationen neu an.

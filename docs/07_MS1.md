## Projektvision

Besonders im Fernstudium sind Studierende stark auf sich allein gestellt und müssen sich vollständig selbst organisieren. Wir geben ihnen mit unserem Lernzeit-Manager ein mächtiges Tool an die Hand. Mit dem Lernzeit-Manager können Studierende ihre gesamte Studienzeit im Groben und im Detail planen, ihren Fortschritt tracken, ihre Lernzeiten organisieren und einen Überblick über das Studium erhalten - alles an einem Ort.

## Lösungsansatz

Der Lernzeit-Manager wird als klassische Web-Anwendung mit getrennten Frontend- und Backend-Schichten umgesetzt, die über eine REST-API kommunizieren:

- **Frontend (Angular):** Single-Page-Application im Browser, kein Installationsaufwand für den Tutor/User. Bildet alle Kernabläufe ab (Lernziele anlegen, Grob-/Detailplanung, Timer, Dashboard) und kommuniziert ausschließlich über HTTP/JSON mit dem Backend.
- **Backend (Flask):** Stellt eine REST-API bereit, die die fachliche Logik kapselt (Lernziel- und Sessionverwaltung, Zeitberechnung, Erinnerungslogik) und die Datenbankzugriffe übernimmt. Enthält zusätzlich die Userverwaltung/Authentifizierung über Flask-JWT-Extended, da eine Datenbank ohne Backend nicht sicher ansprechbar ist.
- **Datenbank (PostgreSQL):** Persistiert Nutzer, Lernziele, Grob-/Detailplanung und erfasste Lernsessions. Das Datenmodell bildet die zwei im Thema geforderten Zeithorizonte ab: Grobplanung/Ziele über mind. 6 Monate und Detailplanung über 1 Monat. Für Tests im Backend wird SQLite in-memory verwendet, für lokale Entwicklung und Produktion PostgreSQL.
- **Deployment:** Frontend und Backend werden als eigene Docker-Container gebaut und auf Railway betrieben. PostgreSQL läuft als Railway Service. Lokal wird dieselbe Container-Struktur zur Entwicklung genutzt.
- **CI/CD:** GitHub Actions prüft bei jedem Push/PR automatisiert Tests und Linting; Deployment auf Railway erfolgt nach erfolgreicher Pipeline (Deployment-Schritt selbst noch nicht implementiert, siehe Aufbau technische Infrastruktur unten).

Anfrageweg: **User → Browser (Angular-SPA) → REST-API (Flask) → PostgreSQL** - die Antwort läuft denselben Weg zurück.

## Annahmen und Beschränkungen

- Ausschließlich kostenlose Tools, da Studierendenprojekt.
- Userverwaltung und Backend werden benötigt, da eine Datenbank erforderlich ist - rein über das Frontend nicht lösbar.
- Flask ist für das Backend als leichtes Python Backend-Framework gut geeignet und es gibt bereits Erfahrungen im Team damit.
- Angular ist als Frontend-Framework durch die vielen Libraries gut geeignet und es gibt bereits Erfahrungen im Team damit.
- Railway ist für das Deployment gut geeignet, da es automatisierte CI/CD-Pipelines unterstützt und durch Containerisierung die Verbindung von Frontend/Backend/Datenbank vereinfacht.

## Aufbau technische Infrastruktur

- **Repository:** GitHub-Repo (privat), enthält Frontend (Angular, `frontend/`), Backend (Flask, `backend/`) sowie die Docker- und CI-Konfiguration.
- **Container** Je ein eigenes Docker-Image für Frontend und Backend, lokal via Docker Compose gestartet, um die Produktionsumgebung möglichst genau nachzubilden.
- **Hosting (Railway):** Drei Services - Frontend-Container, Backend-Container und PostgreSQL-Plugin - sollen als eigenständige Railway-Services innerhalb desselben Projekts laufen und intern über Railway-Netzwerk/Umgebungsvariablen kommunizieren.
- **CI/CD (GitHub Actions):** GitHub Actions führt bei Push und bei Pull Requests gegen `main` zwei Jobs aus: `backend` (ruff + pytest) und `frontend` (ng lint + ng test). Das Deployment auf Railway nach erfolgreichem Durchlauf geschieht automatisch.
- **Zugriffsweg (Ziel-Architektur):** User → Browser (Angular-SPA, öffentliche Railway-URL) → REST-API (Flask-Backend, ebenfalls über Railway erreichbar) → PostgreSQL (nur intern erreichbar, kein öffentlicher Zugriff).
- **Konfiguration/Secrets:** Lokal über `.env`. Umgebungsspezifische Werte für Railway (DB-Connection-String, Auth-Secrets) sollen über Railway-Umgebungsvariablen verwaltet werden.
